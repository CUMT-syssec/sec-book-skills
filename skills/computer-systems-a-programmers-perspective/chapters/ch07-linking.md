# 第 7 章：链接

## Core Idea

链接器把分散的代码和数据节合并为可执行或共享对象，解析符号并重定位引用。理解目标文件、符号强弱、库顺序、PIC 和动态链接，能系统定位“能编译但不能链接/加载”的问题。

## Frameworks Introduced

- **两步链接模型**：符号解析决定“引用指向谁”，重定位决定“最终地址是多少”。
  - When to use：未定义符号、重复定义、调用到错误实现或地址异常时。
- **目标文件分层检查**：源文件 → 可重定位目标 → 静态库/共享库 → 可执行文件 → 运行时映射。
  - How：在出错层使用 `nm`、`readelf`、`objdump`、`ar`、`ldd` 获取证据。
- **符号强弱规则**：全局已初始化定义通常是强符号；未初始化全局常是弱符号；局部 `static` 不参与跨模块冲突。
  - Failure mode：依赖多重全局定义的偶然解析结果。
- **静态库按需扫描**：链接器按命令行顺序维护未解析引用，只抽取当时需要的成员。
  - How：把依赖者放在被依赖库之前；循环依赖应重构或显式重复/分组。
- **位置无关代码**：用 GOT/PLT 等间接层让共享对象不依赖固定加载地址。

## Key Concepts

- **ELF**：Linux 常用的可重定位、可执行和共享对象格式。
- **节**：目标文件中的代码、已初始化数据、未初始化数据、只读数据和元数据区域。
- **符号表**：定义与引用的名称、绑定、类型、节和大小信息。
- **重定位条目**：告诉链接器在哪里、按何种规则修正地址。
- **静态库**：多个可重定位目标的归档，链接时按需复制成员。
- **共享库**：加载或运行时映射，可由多个进程共享代码页。
- **库打桩**：在编译、链接或运行时拦截函数调用的技术。

## Mental Models

- 链接错误先分为“名字问题”和“地址问题”。
- 库顺序不是风格问题，而是单向扫描算法的输入。
- 动态链接把一部分地址绑定推迟到装载或首次调用时。

## Anti-patterns

- **在头文件定义可写全局变量**：多个翻译单元会产生重复或模糊符号。
- **用更改库顺序掩盖循环依赖**：构建暂时通过，但模块边界仍脆弱。
- **假设本机能加载就代表部署可用**：运行时搜索路径、ABI 和库版本可能不同。
- **无边界使用运行时打桩**：会影响可观测性、递归调用和安全边界。

## Code Examples

```sh
gcc -c main.c -o main.o
gcc -c util.c -o util.o
ar rcs libutil.a util.o
gcc main.o -L. -lutil -o app

nm main.o
readelf -S -s -r main.o
objdump -dr main.o
ldd ./app
```

- **What it demonstrates**：分别检查编译产物、符号、节、重定位和运行时共享库依赖。

## Reference Tables

| 症状 | 首查对象 | 常见原因 |
|---|---|---|
| undefined reference | 符号表、库顺序 | 未定义、未抽取库成员、名称重整 |
| multiple definition | 强/弱符号与头文件 | 重复全局定义 |
| 能链接但不能启动 | 动态依赖与搜索路径 | 缺库、ABI/版本不匹配 |
| 调错函数 | 符号绑定、打桩、加载顺序 | 同名覆盖或预加载 |
| 运行地址错误 | 重定位、PIC/GOT/PLT | 非 PIC、损坏或不兼容对象 |

## Worked Example

`main.o` 引用 `foo`，`liba.a` 中的成员定义 `foo`。若命令是 `gcc -la main.o`，扫描库时尚无未解析的 `foo`，成员不会被抽取；之后扫描 `main.o` 才出现引用，最终报未定义。改为 `gcc main.o -la` 后，链接器看到引用再扫描库，成员被抽取。诊断应通过 `nm main.o` 和 `nm liba.a` 确认引用/定义，而不是盲目添加库。

## Key Takeaways

1. 先分清符号解析与重定位，再选择工具。
2. 让跨模块符号最小化，文件内部对象优先使用 `static`。
3. 静态库顺序必须反映依赖方向。
4. 共享库节省磁盘与内存，但把一部分失败推迟到加载期。
5. 部署验收必须检查实际运行时加载的库，而不只看链接成功。
