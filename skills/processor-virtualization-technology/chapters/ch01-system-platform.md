# 第1章：系统平台

## Core Idea

本章构造后续 VMX 实验的共同运行底座：同一套汇编源码可按 32 位或 64 位目标生成，在多处理器平台上依次完成 Stage 1、Stage 2、Stage 3，并以稳定的数据区、分页、IPI 调度和调试记录机制隔离“平台启动”与“虚拟化实验”。设计重点不是某个例子的功能，而是让每个处理器在进入 VMX operation 前拥有一致、可观察、可寻址的上下文。

## Frameworks Introduced

- **三阶段启动框架**
  - When to use：需要从引导环境逐步建立分页、SMP 和 long mode，同时保持 32/64 位实验共享代码时。
  - How：Stage 1 在 32 位未分页保护模式中识别处理器、分配 PCB/LSB 并启动 AP；Stage 2 建立 PAE 分页并作为 legacy 最终环境；定义 `X64` 时继续到 Stage 3，建立 IA-32e 页表并进入 64-bit 模式。每阶段以 BSP/AP 分工、阶段锁和完成计数形成屏障。
- **每处理器状态 + 全局状态分层**
  - When to use：多核启动、调度和 VMX 状态不能依赖全局单例时。
  - How：每个逻辑处理器独占一个 PCB，以 `GS` 访问；全平台共享唯一 SDA，以 `FS` 访问；PCB 保存到 SDA、SRT、LSB、VMX 管理记录的指针，SDA 保存处理器计数、阶段锁、IPI、页表池和调试记录等全局协调信息。
- **物理地址/虚拟地址双视图**
  - When to use：相同结构需要跨未分页、PAE 和 IA-32e 阶段存活时。
  - How：关键地址字段统一为 64 位，并同时保留 virtual base 与 physical base。Stage 1 使用物理基址；进入 Stage 2/3 前切换为线性地址，而需要交给硬件的结构仍显式使用物理指针。
- **能力开关驱动的统一构建**
  - When to use：host/guest、x86/x64 与调试版本需要从同一源码派生时。
  - How：`X64` 决定 Stage 2/3；`GUEST_ENABLE` 加入 guest；`GUEST_X64` 仅在 64 位 host 下有效；`DEBUG_RECORD_ENABLE` 开启记录；`STAGE1/2/3` 隔离阶段代码。

## Key Concepts

- **Stage 1**：32 位、未分页保护模式；完成基础数据结构、处理器发现与 AP 启动。
- **Stage 2**：32 位、PAE 分页保护模式；既是 32 位构建的终态，也是进入 Stage 3 的过渡基础。
- **Stage 3**：IA-32e 下的 64-bit 模式；完成 64 位页表、处理器收尾并进入 VMX root operation。
- **PCB（Processor Control Block）**：每逻辑处理器私有的 8KB 控制块，记录索引、状态、上下文、APIC、VMX 能力与 VMCS/VMXON 相关管理信息。
- **SDA（System Data Area）**：所有处理器共享的系统数据区，承担全局资源目录与同步中心。
- **LSB（Local Store Block）**：每处理器私有的本地键盘、显示和定时信息，使处理器焦点切换不污染其他 CPU 的交互状态。
- **BSP / AP**：BSP 负责全局初始化、广播 `INIT-SIPI-SIPI` 和阶段推进；AP 被唤醒后完成本地初始化并通过计数/锁汇合。
- **DRS（Debug Record Structure）**：保存寄存器、RIP/RFLAGS、文件、行号和备注的调试记录节点。
- **PAE / IA-32e 分页**：Stage 2 使用固定三级页表区域；Stage 3 固定 PML4T/PDPT，并从 PT pool 动态分配 PDT/PT。

## Mental Models

- 把启动过程看成**带屏障的状态机**：任何处理器只有在本阶段本地不变量成立、全局完成计数满足后，才能进入下一阶段。
- 把 `GS:PCB` 看成“当前 CPU 的线程本地存储”，把 `FS:SDA` 看成“内核全局控制面”；先判断数据归属，再决定放入哪一层。
- 把地址看成**阶段相关的解释**：字段宽度可以固定，但同一对象在未分页与分页阶段的可用指针不同，不能用虚拟指针替代硬件要求的物理指针。
- 把 IPI 调度看成异步消息：发送成功只表示任务已投递；需要完成语义时，必须使用等待版本或显式信号。

## Anti-patterns

- **跨阶段隐式复用地址**：在 Stage 1 保存物理地址后，进入分页环境仍按普通指针使用，会把“同一数值”误当成“同一映射”。
- **把每 CPU 状态塞入 SDA**：导致处理器间覆盖、锁竞争和 VMX 上下文归属不清；处理器私有状态应进入 PCB/LSB。
- **AP 自行推进阶段**：绕过 BSP 的阶段锁和完成计数会形成竞态，尤其会破坏页表及共享结构只初始化一次的假设。
- **长任务运行在 IPI 上半部**：中断期间外部中断受抑制；普通调度应把目标例程放到 BottomHalf，先完成 EOI/返回路径。
- **强制覆盖已有映射**：只有明确需要时才使用 `FORCE`；默认应检查页大小、R/W、U/S、XD 等层级权限是否一致。
- **依赖虚拟机报告代表真实硬件**：VMware 暴露的 CPU/VMX 能力是虚拟化后的结果，涉及硬件限制的例子必须在真实机器重新验证。

## Reference Tables

| 阶段 | 处理器模式 | 分页 | 主要职责 | 完成后状态 |
|---|---|---|---|---|
| Stage 1 | 32 位保护模式 | 关闭 | PCB/LSB、处理器枚举、AP 唤醒、基础能力采集 | 进入 Stage 2 前屏障 |
| Stage 2 | 32 位保护模式 | PAE | 固定页表区、SMP 服务、32 位最终运行环境 | AP 通常进入 HLT；BSP 运行主体 |
| Stage 3 | IA-32e 64-bit | 四级分页 | 动态页表池、64 位上下文、VMX 初始化 | 各 CPU 可进入 VMX root operation |

## Key Takeaways

1. 先建立可重复、可观察的平台状态，再讨论 VMX；否则虚拟化故障会与启动、分页、SMP 故障混在一起。
2. Stage 1/2/3 是一组逐步增强的不变量，不是三个可随意跳转的入口。
3. PCB、LSB 负责处理器私有性，SDA 负责全局协调；`GS`/`FS` 的分工应贯穿所有平台代码。
4. 页表管理必须同时验证地址对齐、层级权限和映射占用状态；Stage 3 的下级页表应从受控 pool 分配。
5. IPI 调度默认是异步的；同步等待、NMI 强制投递和不可返回跳转必须作为不同语义使用。
6. DRS 的价值在于捕获“发生时”的处理器上下文，适合定位跨阶段、跨 CPU 的瞬时错误。
