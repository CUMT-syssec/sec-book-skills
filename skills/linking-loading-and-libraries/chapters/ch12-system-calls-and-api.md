# Chapter 12: 系统调用与 API

## Core Idea

系统调用是用户态进入内核服务的受控边界；Windows API 又在应用与底层系统调用之间提供稳定、可演化的用户态接口。接口层级决定兼容性、权限和排障位置。

## Frameworks Introduced

- **特权边界模型**：用户态不能直接访问受保护资源，必须通过定义明确的入口切换到内核态。
  - When to use：权限、系统资源访问、用户态/内核态性能或安全分析。
  - How：确认调用号/服务、参数传递、入口机制、内核验证、返回值与错误码。
- **稳定接口层**：用 API 包装不稳定或平台相关的底层机制。
  - When to use：需要向后兼容、参数验证或跨版本演化。
  - How：区分公开 API 契约与内部 syscall 编号/实现；只依赖承诺稳定的层。
- **调用轨迹追踪**：`应用 → CRT/库 → API wrapper → syscall stub → kernel service`。

## Key Concepts

- **系统调用**：操作系统向用户程序提供内核服务的接口。
- **特权级**：限制不同执行环境可执行的指令和资源访问。
- **中断/陷阱/快速系统调用**：从用户态进入内核的机制家族。
- **调用号**：选择内核服务的标识。
- **Windows API**：应用程序主要依赖的 Windows 用户态接口层。
- **子系统**：Windows 在内核服务之上组织不同应用环境的架构。
- **错误返回**：系统调用与 API 可能使用不同错误传递约定。

## Mental Models

- 把 syscall 看成受验证的 RPC：跨越保护边界传递操作和参数。
- 把 Windows API 看成兼容契约，不要把其当前内部 syscall 映射当稳定事实。
- 系统调用次数是性能线索，但减少次数不能以破坏正确性、缓冲或安全为代价。

## Anti-patterns

- **应用直接依赖未承诺稳定的内部 syscall 编号**：系统更新可能改变实现。
- **把 API 失败等同内核拒绝**：用户态包装层也可能验证、转换或缓存。
- **只检查返回值不读取规定的错误通道**：会丢失根因。

## Worked Example

Linux 用户程序请求读取文件时，CRT 准备参数并进入系统调用封装；stub 按 ABI 把调用号与参数放入约定寄存器，执行陷入指令；内核验证文件描述符、用户缓冲区和权限，完成或阻塞 I/O，再以约定返回结果/错误。Windows 上公开路径通常先经过 `ReadFile` 等 API，内部实现细节不应成为应用契约。

## Key Takeaways

1. 系统调用既是功能接口也是安全边界。
2. 公共 API 与内部 syscall 的稳定性等级不同。
3. 参数必须按用户态/内核态 ABI 解释并验证。
4. 调用轨迹要覆盖包装层、入口 stub 和内核服务。
5. 性能分析应把调用次数、数据量、阻塞和缓存共同考虑。
