# Chapter 2: 编译和链接

## Core Idea

一条构建命令隐藏了预处理、编译、汇编和链接。可靠排障的第一步是拆开流水线，检查每一阶段的输入、输出和契约。

## Frameworks Introduced

- **构建流水线分解**：`source → preprocessed → assembly → object → executable`。
  - When to use：宏展开异常、编译优化疑问、undefined reference、链接到错误库。
  - How：让工具停在目标阶段；保存中间产物；比较“首次偏离预期”的输出。
- **编译器阶段模型**：词法分析、语法分析、语义分析、中间代码、优化、目标代码生成。
  - When to use：区分语法/类型问题与代码生成、优化或 ABI 问题。
  - How：先判断错误属于语言规则还是目标平台实现，再选择 AST/IR/汇编证据。
- **模块拼装模型**：每个编译单元先独立产生目标文件，链接器再处理跨模块引用。

## Key Concepts

- **预处理**：展开宏、条件编译和头文件包含。
- **编译**：把预处理结果转换为汇编或内部目标表示。
- **汇编**：把汇编指令编码为机器码和重定位信息。
- **链接**：合并目标文件，解析符号并修正地址引用。
- **静态库**：按需参与链接的一组目标文件归档。
- **构建**：IDE 对上述阶段的编排，不是单一技术动作。

## Mental Models

- 把 IDE 的 Build 按钮看成流水线调度器，而不是编译器本身。
- 把头文件看作声明传播机制，不是实现的唯一实体。
- 用“本文件能否独立编译”和“全程序能否完成链接”区分局部与全局约束。

## Anti-patterns

- **只重复执行完整构建**：会丢失哪一阶段首次出错的信息。
- **把编译错误与链接错误混称**：二者证据和修复对象不同。
- **依赖 IDE 默认参数却不知道实际命令**：换环境后难以复现。

## Worked Example

对 `hello.c` 分四步处理：先生成预处理文件观察宏和包含；再生成汇编观察代码选择；汇编成 `.o` 后检查符号与重定位；最后交给链接器并生成 map。若最终引用缺失，而 `.o` 中该符号是未定义且目标库中存在定义，问题就缩小到库选择、顺序、可见性或 ABI，而不是 C 语法。

## Key Takeaways

1. 构建问题要以中间产物为证据。
2. 编译单元只解决局部语义，链接解决全局名字与地址。
3. 优化发生在流水线中，不能只从源代码猜最终机器行为。
4. 复现构建必须记录实际命令、版本和输入。
